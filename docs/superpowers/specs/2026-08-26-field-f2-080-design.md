# Field Macro F2 0.80 Program Design

## Goal

Build a reviewed, reproducible path to at least 0.80 macro F2 on a frozen field-recorded test set.

The result must preserve ARANYA AI's browser-first architecture. It must also satisfy the existing detector, dataset, evaluation, and model-bundle contracts.

## Success criteria

The program succeeds only when all of these conditions hold:

- The frozen field test set reaches at least 0.80 macro F2 across the five targets.
- Every promoted target reaches at least 0.70 F2.
- Each promoted target has at least 100 independent positive test recording groups.
- Test groups are isolated from training and validation by source, session, capture, device, location, and near-duplicate lineage.
- Thresholds and model choices use validation data only.
- Event recall does not fall below the current A1 browser baseline.
- False positive events per background hour do not exceed A1.
- Browser P50 and P95 inference latency, model size, and memory use are measured.
- A ranger or product owner approves the false-alert budget for each promoted target.
- The release includes a model bundle, model card, dataset version, split version, environment lock, known failures, and parity vectors.

The 0.80 target is a field test target. Exploratory validation scores do not satisfy it.

## Project constraints

The target order remains exactly:

1. `gunfire`
2. `chainsaw`
3. `metal_tool_activity`
4. `fire`
5. `vehicle`

The detector returns five independent scores. Several targets may be positive in one window. `background` is an all-zero verified negative and is never a model output.

Browser inference remains local. The production candidate must not require a backend, cloud inference, or live retraining. It consumes mono 16 kHz PCM from the existing upload and rolling microphone paths.

The existing event builder, event store, alerts, maps, incidents, and analytics remain unchanged unless a versioned contract requires an explicit update. Physical sensors, LoRaWAN, and localization remain simulated or future work.

Raw audio, embeddings, checkpoints, generated reports, and exported models stay under ignored `ml/work/` paths. Git tracks reviewed metadata, annotations, licenses, frozen splits, code, contracts, model cards, and small parity fixtures.

Gunfire and fire data collection must use authorized controlled sources or licensed recordings. The program must preserve privacy and sensitive location controls.

## Delivery strategy

The program uses a data-first teacher and student design.

Large pretrained teacher models establish the best attainable field accuracy for each target. Candidate families include YAMNet, PANNs, AST, and BEATs. These models run only in the offline Python workspace.

The best teacher outputs guide a compact multi-output student. The student is exported to TensorFlow.js and runs in the existing browser inference path. If one compact model cannot preserve the required quality, a small gated specialist may be added for a weak target. Browser latency and size gates still apply.

This design avoids committing to an ensemble before evidence supports it. Every added model must improve frozen validation results enough to justify its runtime cost.

## Dataset architecture

### Dataset versions

Create a new field dataset version under `ml/datasets/`. It contains source records, recording metadata, interval annotations, licenses, review state, and frozen group splits.

Raw recordings stay under `ml/work/raw/`. Derived audio windows stay under `ml/work/derived/`. Dataset builders produce deterministic manifests from tracked metadata and local audio.

Every dataset build receives a content fingerprint. A changed source file, annotation, split, preprocessing setting, or target mapping changes the fingerprint.

### Collection matrix

Field collection must cover the conditions the browser will encounter:

- multiple microphone and device types;
- multiple forest and forest-edge locations;
- near, medium, and distant events;
- dry, wet, windy, and quiet conditions;
- daytime and nighttime backgrounds;
- single events and overlapping sounds;
- clean target examples and low signal-to-noise examples.

The minimum release gate is 100 independent positive test groups per promoted target. The working target is at least 500 independent positive groups per target across all splits. Rare classes may use licensed external audio for training, but the final test support must remain field-recorded and representative.

### Negative data

Verified target-free background time is required for event-level false-alert measurement. Important hard negatives include:

- rain, wind, thunder, insects, birds, and mammals;
- speech, music, doors, and handling noise;
- generators, pumps, engines, motorcycles, and distant traffic;
- axes, hammers, construction, and non-target metal impacts;
- crackling leaves, cooking sounds, and safe non-fire crackle sources;
- impulsive noises that resemble gunfire.

Unreviewed time is never treated as negative.

### Annotation and review

Each target event receives start and end timestamps. Reviewers may assign several targets to the same interval. They also mark uncertain events, clipping, corruption, privacy restrictions, and unusable audio.

Validation and test annotations require human review. A second reviewer checks ambiguous positives, every disagreement, and a sampled set of negatives. The adjudicated label becomes the released label. Training may use singly reviewed labels only when the manifest records that status.

### Leakage controls

Group assignment happens before window generation. All related clips remain in one split. The grouping key includes source lineage, original recording, session, device, location, date block, and near-duplicate family when available.

Audio fingerprints detect exact and near duplicates before freezing splits. Test groups never move. Once a test result affects a decision, the next model program uses a new test version.

## Training architecture

### Window generation

Training uses 0.96-second windows with a 0.48-second hop by default. The configuration remains versioned. Positive windows use interval overlap rules. Negative windows come only from fully reviewed target-free time.

Training supports variable context experiments without changing the browser input contract. Longer context models aggregate several consecutive 0.96-second embeddings.

### Augmentation

Training-only augmentation covers field variation. It may add reviewed background audio, gain changes, time shifts, mild filtering, device impulse responses, and codec artifacts. It must preserve target identity.

Mixing may create valid multi-label windows. Augmentation records its seed and configuration. Validation and test audio never receive stochastic augmentation.

### Teacher benchmark

Each teacher family receives the same dataset fingerprint and split. The benchmark includes:

- frozen embeddings with balanced logistic heads;
- frozen embeddings with a small MLP;
- partial fine-tuning when hardware and licenses allow it;
- target-specific heads for weak classes;
- temporal pooling over consecutive frames.

Teacher selection uses validation macro F2, per-target F2, PR-AUC, and the false-alert budget. Test scores never choose a teacher.

### Hard-negative mining

The selected teacher scans reviewed background recordings. Reviewers inspect the highest-scoring false detections. Confirmed hard negatives enter the next training dataset version.

Each mining round freezes its candidate list, review decisions, and dataset fingerprint. A round stops when validation gains flatten or false alerts meet the approved budget.

### Student model

The first student is one compact five-output network. It learns from reviewed labels and teacher probabilities. The loss combines binary classification, distillation, and class-balanced weighting.

If one target remains below its gate, the program may add one compact specialist or use target-weighted fine-tuning. A specialist is accepted only when its validation gain survives bootstrap confidence intervals and its browser cost remains acceptable.

### Calibration and event rules

Each target receives an independent calibrated score and threshold. Calibration uses validation data. Threshold selection maximizes event-level F2 while satisfying the false-alert budget.

Event formation applies target-specific persistence, cooldown, and duplicate suppression. These rules use validation sequences only. The test split remains untouched.

## Evaluation architecture

### Required metrics

Every candidate report includes:

- per-target precision, recall, F1, F2, PR-AUC, and calibration error;
- macro F1 and macro F2;
- event precision and event recall;
- false positive events per background hour;
- detection delay and duplicate events;
- bootstrap confidence intervals;
- P50 and P95 browser latency;
- model download size and peak browser memory;
- slices by unseen source, session, device, location, distance, weather, and signal-to-noise range when available.

Clip-level and event-level metrics remain separate. A high clip score cannot replace event evaluation.

### Model selection

The model registry records every experiment configuration, dataset fingerprint, code commit, seed, metrics path, and artifact hash. The selection report ranks candidates using validation data.

The frozen test set is evaluated once for the selected release candidate. A failed test candidate does not trigger tuning against the same test version.

### Promotion

Promotion happens per target. A model bundle may mark some targets `promoted` and others `candidate`.

A target passes only when it meets its F2 floor, preserves A1 event recall, respects the false-alert budget, has enough independent test support, and passes browser parity tests.

## Browser integration

The exported student uses TensorFlow.js or another runtime accepted by `contracts/model-bundle.v1.schema.json`. It includes the exact preprocessing ID, class order, thresholds, dataset version, split version, and SHA-256 digest.

Python and browser parity vectors use the same short PCM fixtures. Scores must stay within a documented tolerance. Event decisions must match exactly at threshold boundaries.

The browser loads the candidate through the existing model adapter boundary. The current A0 or A1 path remains available as a safe fallback until the candidate passes all promotion gates.

Inference must stay off the audio rendering thread. The rolling PCM buffer and event flow remain the source of live input and detections.

## Failure handling

Training stops when required audio, labels, licenses, split assignments, or local model files are missing. It does not download models during a run.

Dataset builds reject missing files, split leakage, duplicate IDs, invalid intervals, unknown targets, unreviewed negatives, and changed frozen assignments.

Experiment outputs reject mismatched fingerprints, model settings, seeds, or preprocessing configurations. Partial artifacts never count as completed runs.

Browser loading validates the model hash, input contract, output shape, and class order. A failed candidate load falls back to the current supported detector and records the failure without inventing a detection.

## Testing strategy

Unit tests cover manifest rules, interval-to-window labels, augmentation determinism, duplicate detection, metrics, calibration, event formation, model-bundle validation, and fingerprint safety.

Integration tests run small synthetic training jobs. They verify split isolation, validation-only selection, artifact creation, deterministic replay, and failure behavior.

Parity tests compare Python and browser preprocessing, scores, thresholds, and event decisions. Browser performance tests measure representative desktop and mobile hardware.

Data tests run on every tracked dataset change. Full teacher training, field scans, and browser benchmarks run as explicit release jobs because they require local data and compute.

## Program stages

### Stage 1: Measurement foundation

Add event annotations, reviewed background hours, leakage checks, event metrics, calibration error, confidence intervals, and experiment registry support.

Exit when the current A1 and repaired log-mel models have valid event-level reports.

### Stage 2: Field dataset v1

Collect, review, license, group, and freeze representative field data. Build the collection matrix and support dashboard.

Exit when every target has adequate validation support and the test split meets the 100-group release floor.

### Stage 3: Teacher benchmark

Benchmark pretrained model families and temporal heads on one frozen dataset version. Select by validation evidence.

Exit when one teacher exceeds 0.75 validation macro F2 and no target is below 0.60, or when the benchmark proves data remains the limiting factor.

### Stage 4: Hard-negative rounds

Scan reviewed background hours, adjudicate false detections, and retrain on versioned datasets.

Exit when the selected teacher reaches at least 0.82 validation macro F2, every target reaches 0.72, and the false-alert budget passes.

### Stage 5: Browser student

Distill the teacher into a compact student, export it, and add parity and performance tests.

Exit when the student retains at least 98 percent of teacher macro F2 and passes browser runtime gates.

### Stage 6: Frozen field test and promotion

Evaluate the selected student once on the frozen field test set. Produce the release bundle and model card.

Exit when the success criteria pass. If they do not pass, freeze the result, create a new dataset and test version, and begin the next program cycle without tuning on the old test.

## Non-goals

This program does not build sensor firmware, LoRaWAN transport, a backend, automatic cloud retraining, or real multi-node localization.

It does not guarantee 0.80 before enough reviewed field data exists. It builds the shortest defensible path to that result.

It does not commit raw audio, large model files, generated metrics snapshots, or point-in-time audit reports.

## Final deliverables

- A versioned field dataset catalog and frozen split.
- Reviewed interval annotations and verified background hours.
- A reproducible teacher benchmark and experiment registry.
- Versioned hard-negative mining rounds.
- A compact browser student and export pipeline.
- Python and browser parity vectors.
- Event-level evaluation with confidence intervals and field slices.
- A validated model bundle and model card.
- Per-target promotion decisions with known failure cases.
